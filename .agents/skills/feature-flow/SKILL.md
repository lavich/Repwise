# Флоу изменения: OpenSpec → Orca-ворктри → перекрёстное ревью

[openspec/config.yaml](../../../openspec/config.yaml), а когда появится — AGENTS.md,
содержат правила проекта, на которые опирается флоу: стек, структуру, обязательную
проверку, коммиты, выпуски. Прочитать их первыми; навык задаёт только порядок работы.
`.claude/skills/feature-flow` — ссылка на эту папку: править здесь.

Общение с пользователем — по-русски, кратко. Решения, которые меняют то, что видит
пользователь Repwise, или то, как хранятся его данные, принимает пользователь.

Любая правка, коммит и пуш во флоу — план, реализация, исправления после ревью —
делаются в Orca-ворктри. Основная копия репозитория стоит на `main` и только
подтягивает изменения. Ворктри создаётся с `--setup run`; если хук настройки ничего
не ставит — сначала установить зависимости. Ветку не пушить, пока обязательная
проверка не завершилась с кодом 0: связывать через `&&`, не `;`.
Продолжить ветку, которая уже есть на remote:
`orca worktree create --name <name> --no-parent --setup run --base-branch origin/<branch> --json`,
пушить через `git push origin HEAD:<branch>` — Orca называет локальную ветку иначе.

Вызов флоу — разрешение пушить его ветки и открывать их PR, и только это: мерж и
теги требуют отдельного разрешения.

## Когда OpenSpec не нужен

Изменение OpenSpec заводится для новой возможности или правки поведения, которое
видит пользователь. Баг, после исправления которого приложение ведёт себя так, как
уже описано в `openspec/specs/`, идёт без него: ворктри, исправление, проверка, PR.
Если баг упирается в формулировку спецификации, которая описывает реализацию, а не
поведение, эта строка правится прямо в том же PR — без proposal, design и tasks.

Одно изменение — один ворктри и одна ветка от плана до мержа: план, реализация и
исправления после ревью — коммиты этой ветки, в `main` они попадают одним PR. План
отдельно не мержится. Второй ворктри от `main` — только для архивации.

## 1. Обсуждение

- Разобрать запрос по коду и спецификациям в `openspec/specs/`: цифры и `file:line`,
  а не впечатления. Незнакомую библиотеку или API проверить коротким скриптом во
  временной папке вне репозитория.
- Предложить 2–3 варианта с рекомендацией и назвать области кода, которые каждый
  затрагивает.
- Решение пользователя записать дословно с датой — оно пойдёт в proposal.

## 2. План: OpenSpec в Orca-ворктри

- Ворктри от свежего `main` — тот же, что будет и для реализации:
  `orca worktree create --name <change> --no-parent --setup run --json`, затем
  `orca worktree set --worktree path:<path> --workspace-status in-progress --json`.
- Изменение — по навыку `openspec-propose`: `openspec new change <name>`, затем
  proposal, design, specs и tasks, каждый по
  `openspec instructions <artifact> --change <name> --json`. Артефакты по-русски,
  структурные заголовки OpenSpec и SHALL/MUST — по-английски. В proposal требование
  пользователя отделено от предлагаемого объёма; у каждой задачи — её проверка.
- Если изменение зависит от другого открытого изменения — сказать об этом и указать
  порядок архивации первой строкой `tasks.md`. MODIFIED-требование — полным текстом
  в том виде, какой оно примет после изменения, архивируемого раньше, со всеми
  существующими сценариями.
- `openspec validate <name> --strict` проходит.
- Комментарий ворктри держать актуальным:
  `orca worktree set --worktree path:<path> --comment "…" --json`.

## 3. Перекрёстное ревью плана

- Независимый ревьюер — субагент или отдельная сессия агента (например,
  `orca worktree create --agent codex`), строго только чтение, временные файлы — вне
  репозитория. Задача: сверить каждое утверждение плана с кодом (`file:line`); найти
  всех потребителей, которых затрагивает изменение, пробелы, противоречия между
  артефактами, пересечения с другими открытыми изменениями в `openspec/changes/` и
  нарушения правил проекта. Вывод: Blocking / Serious / Minor, у каждого — сценарий
  отказа и исправление.
- Самые неожиданные находки проверить самому. Спорные решения вынести пользователю,
  остальное исправить; повторить ревью, если правки крупные.
- План — первый коммит ветки изменения.

## 4. Реализация

- В ворктри плана; если `main` ушёл вперёд — `git rebase origin/main` до начала.
- Реализовать самому или передать агенту в этом ворктри
  (`orca agent launch --agent <id> --worktree path:<path> --prompt "…" --json`) —
  оба пути допустимы. В задании агенту — папка изменения, что ему можно кроме
  коммитов (пуш, открыть PR) и что он сообщает: выполненные задачи, проверки с их
  выводом, коммиты, что осталось. Пользователь может расширить задание в чате
  агента, которого не видно, поэтому перед отчётом о переданном изменении смотреть
  его реальное состояние — ветку, PR, — а не задание. Удаление ворктри закрывает чат
  агента.
- Базовый прогон тестов до правок. Задачи — по порядку `tasks.md`, тест на каждую;
  отклонения от дизайна записать в раздел «Реализация» в `design.md`; отметить `- [x]`.
- Обязательная проверка — набор проверок CI; сказать, какие запускались. Пока CI в
  проекте нет — назвать, какие проверки запускались, и что обязательной проверки
  ещё нет.
- Изменённый экран — проверить скриншотом временного Playwright-скрипта на ширине
  десктопа и телефона, затем скрипт удалить.

## 5. Перекрёстное ревью кода

- Два независимых ревьюера параллельно, по областям — например, домен и данные
  (модели, хранилище, API, миграции) и то, что видит пользователь (экраны, тексты,
  стили, тесты), — только чтение, по diff ветки с `main`: `git diff origin/main...HEAD`.
- Блокирующее доказать тестом, который падает без исправления и проходит с ним.
  Исправить, затем снова полная проверка.

## 6. PR и мерж

- Коммит, `git push`, `gh pr create` с описанием: что сделано, что не вошло и
  почему, и план проверки чекбоксами — запущенные проверки и ручные, отмеченные
  только после того, как их кто-то выполнил. Затем `--workspace-status in-review`
  у ворктри.
- Мерж — только по явному разрешению пользователя на этот PR. Разрешение из прошлой
  задачи или прошлого PR не переносится. В фоне `gh pr checks <n> --watch`, затем
  сообщить итог и ждать. PR, отставший от `main`, — `gh pr update-branch <n>` и
  снова проверки перед мержем. По разрешению и при всех проверках зелёных —
  `gh pr merge <n> --squash`, если пользователь не просит сохранить коммиты.
- После мержа: `git pull --ff-only` в основной копии, `--workspace-status completed`
  у ворктри; смерженные ворктри удалить `orca worktree rm`, проверив, что в них нет
  незакоммиченных изменений.
- Архивация — отдельным PR из свежего ворктри от обновлённого `main`:
  `openspec archive <name> --yes`, затем `openspec validate --all --strict`, коммит
  `chore(openspec): archive <name>`. Мержится тоже по отдельному разрешению.
- Если изменение стоит выпустить — сказать об этом. Тег выпуска не создавать и не
  пушить без явного разрешения.
